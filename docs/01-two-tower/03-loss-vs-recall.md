# 03｜loss 会降，推荐准不准？

第 02 篇把训练目标写出来了，模型也训起来了。但训练 loss 不是交付物——推荐系统是按"用户能不能在列表里看到他想要的东西"评价的。

这一篇做两件事：把评估这件事拆开讲清楚；然后看第一轮结果，以及一轮**合理、但没找到根因**的排查。

先说清楚为什么必须自己写评估：训练时每一行的候选是同一个 batch 里的 B 个物品，而用户真正面对的是全部 3,533 部电影。**候选集不同，两个数字之间没有可比性。** 而且 loss 衡量的是"正确那一个在候选里排得够不够前"，推荐关心的是"前 K 个里有没有他真的会点的"——一个是概率，一个是集合命中。

## 一、训练侧三个不报错的坑

写评估之前，先把训练侧三件容易静默出错的事记下来。它们的共同点是：**不会报错，指标照样出数，只是数不对。**

### 1. 训练模式和推理模式

`model.eval()` 会在评估代码里被调用，而 `model.train()` 必须在训练循环开头切回来。

当前模型只有 Embedding，没有 Dropout / BatchNorm，写不写结果一样。但只要以后加了任何对训练状态敏感的层，忘了切回来就会让模型一直停在推理模式——而且只有在"评估之后继续训练同一个模型"这种顺序下才暴露，很难查。

规矩很便宜：进 epoch 循环先 `model.train()`。

### 2. 随机状态漂移

DataLoader 的 `shuffle` 用的生成器是有状态的。如果先用同一个 loader 跑一个 30 batch 的快速检查，再接着做正式训练，那么正式训练看到的 batch 顺序就取决于**那个检查跑没跑、跑了几次**。

结果是：同一份代码、同一个种子，换个执行顺序就得到不同的指标。

做法是正式实验前重新设种子、重新建 loader。这也是所有对照实验的前提——两组必须看到完全相同的 batch 顺序，否则最后差异是改动带来的还是随机性带来的，分不清。

### 3. 平均 loss 的分母

用 `max_batches` 做快速检查时，平均 loss 要除以**实际跑过的批次数**，不是数据集的总批次数。写错了不报错，只会让打印出来的数偏小，而且看上去挺合理。

## 二、评估协议

### 编码全部 item

Two-Tower 的检索优势在这里第一次兑现：item 向量只跟 item 有关，可以一次性全部算好，得到 `[I, D]`；用户向量按批算，`[Q, D]`；两者相乘得到 `[Q, I]`。

当前只有 3,533 个候选，直接算满就够，不需要向量检索库。这也是为什么一开始就强调 item 侧可以提前算——换成上亿候选时，省的就是这一步。

`Q × 3533` 这个分数矩阵不算小，用户多的时候要分批，不然内存顶不住。

### 为什么必须先过滤 seen items

如果把用户训练时已经交互过的电影继续放进候选，模型可能靠"重复推荐已知物品"拿到虚高结果。这几乎是白送的分数，而且这种作弊**不会体现在 loss 上**——loss 根本不知道评估是怎么做的。

做法是按用户整理 train seen items，把对应分数设成 `-inf`，再取 top-K。

过滤的是 train history。validation target 对当前用户没有出现在 train 中，所以它仍是合法候选——这不表示该电影没被其他用户看过。

### leave-one-out 与 full-ranking

当前每个评测用户只留了**一条** target（下一次交互）。这是 leave-one-out：每个用户贡献一个"正确答案"，指标在所有用户上取平均。

评估范围是全部 item，叫 full-ranking。另一种常见做法是采样一批候选再排序，省算力，但会额外引入候选采样误差——采样分布不同，指标就不可比。这里 3,533 个候选撑得住精确计算，所以不采样。

但 full-ranking 不等于"无偏"。曝光机制、数据缺失、用户偏好随时间漂移都还在，只是评估本身没有再加一层采样噪声。

## 三、指标

### Recall@K

```text
Recall@K = (1/|U|) · Σ_{u∈U} 1[ target_u ∈ TopK(u) ]
```

每个评测用户只判断一次：他那条 target 在不在前 K 个里。因为每人只有一个 target，这个值同时就是命中率。

### NDCG@K

Recall 不看位置——排第 1 还是第 20 都算命中。但推荐列表是有顺序的，靠前显然更有价值。

```text
DCG@K  = Σ_{r=0}^{K-1} rel_r / log2(r + 2)          排名 r 从 0 开始
NDCG@K = DCG@K / IDCG@K
```

`rel_r` 是第 r 位的相关性；单 target 协议下只有命中那一位是 1，其余为 0。

两个容易绊住人的细节：

- **`log2(r + 2)` 里的 `+2`。** r 从 0 开始，而 `log2(1) = 0` 会让第一名权重变成无穷大，所以分母取 `r + 2`：第一名贡献 `1/log2(2) = 1`，第二名 `1/log2(3) ≈ 0.63`。
- **这里 `IDCG@K` 恰好是 1。** IDCG 是"理想排序下的 DCG"——唯一那个 target 排第一位，贡献 `1/log2(2) = 1`。所以单 target 下 NDCG 就是命中时的折损值本身，不用真的算归一化。但要清楚为什么可以省。

### HitRate 什么时候和 Recall 一样

单 target 协议下，HitRate@K（至少命中一个的用户比例）和 Recall@K 数值相同。多 target 时二者才分开：Recall 按命中数累计，HitRate 只看有没有命中。

报告里两个都列不算错，但要知道在当前协议下它们是同一个数，不是两份独立证据。

## 四、第一轮结果

第 01、02 篇的模型是裸查表。第一版训练时给两侧各加了两层 MLP（`Embedding → Linear → ReLU → Linear → normalize`），因为"查表之后再过一个网络能学到更有表达力的映射"是个很自然的假设。它成不成立，第 05 篇用同一套评估结账——这里先看结果。

naive Two-Tower（MLP tower、D=64、temperature=0.2、lr=0.001、5 epochs、不对 false negative 做处理）的真实结果：

| Split | Recall@10 | Recall@20 | NDCG@10 | NDCG@20 |
|---|---:|---:|---:|---:|
| Validation | 0.026678 | 0.047390 | 0.012847 | 0.018000 |
| Test（历史最终评估记录） | 0.024524 | 0.047722 | 0.011842 | 0.017665 |

`Recall@20 = 0.047390` 意味着早先协议下的 6,035 个 validation 用户里，约 4.7% 的下一次交互进了前 20 名。

顺手核对一件小事：把某个用户的 Top-20 和他在 train 里看过的电影求交集，应该是空的（第二节那个过滤生效了）。这只证明评估没作弊，不解释结果为什么差。

> 这张表用的是 MLP tower + lr=0.001。`labs/` 从 embedding-only + lr=0.01 出发，基线是 0.079339。两组都是真实结果，但不能直接横向比——参见 `docs/README.md`。

## 五、一轮没找到根因的排查

Recall 只有 4.7%，第一个合理的怀疑是 temperature：logits 经过 L2 normalize，范围窄，尺度可能不对。

保持其他条件不变，只改 temperature：

| Temperature | Val Recall@10 | Val Recall@20 | Val NDCG@10 | Best epoch |
|---:|---:|---:|---:|---:|
| 0.20 | 0.026678 | 0.047390 | 0.012847 | 5 |
| 0.10 | 0.027506 | 0.048219 | 0.013288 | 5 |
| 0.05 | 0.026843 | 0.047722 | 0.012857 | 5 |

三个 Recall@20 都在 0.047~0.048，变化在小数点后第三位。

**这次排查本身没有做错**：temperature 确实影响训练（第 02 篇讲过它改的是梯度尺度），也确实值得先排掉；一次只改一个变量也守住了。结论是——它不是主要矛盾。

失败分析的价值不在于"猜错了"，而在于**排除法的方向**。既然超参层面只值千分之几，那问题更可能在目标本身。下一轮不调参数，回头检查第 02 篇那个公式里没验证过的假设。

## 六、这一篇的坑

1. **seen-item filtering 不做就是刷分**，而且不会体现在 loss 上。
2. **复用同一个 loader 的两个实验不可比**——随机状态已经漂移。
3. **NDCG 的分母省掉要说得清理由**，不能因为"单 target"就随便写。
4. **分母用错**：评测分母是 3,025（可评测用户），不是 6,038。
