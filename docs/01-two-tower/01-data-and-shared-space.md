# 01｜数据与共享空间

> 本篇的数据切分描述已按 v2 更新；后文若引用历史模型指标，仍属于 v1。当前评估结果以 `artifacts/results.json` 为准。

推荐系统要回答的问题，落到这一步只有一句：给一个用户，从全部电影里挑出他最可能喜欢的 Top-K。

在写模型之前，有两组决定要先做对——数据怎么切、向量怎么放。这两件事错了，后面无论怎么调模型都救不回来，而且**都不会报错**。

## 一、数据：为什么切分必须按时间

### 连续 ID

MovieLens 的原始记录是 `user_id::movie_id::rating::timestamp`。本项目把 `rating >= 4` 当作正反馈，然后做一件事：把原始 ID 重新编号成从 0 开始的连续索引。

这不是洁癖，是 `nn.Embedding` 的工作方式决定的——它按行号查表，索引越紧凑越好。连续化解决两件事：

- 原始电影 ID 是稀疏的（不是每个编号都有片子）。直接当行号会在 Embedding 表里留下成片"永远查不到"的空行，白占显存，参数量统计也会失真。
- 连续化把索引空间压到实际用到的实体数量上；同时"内部索引 ↔ 原始 ID"的对应关系集中在一处管理，反查、调试和输出推荐结果时都方便。

同时保留 `index_to_user` / `index_to_item` 两张反向映射。模型只看索引，但输出"给用户 1 推荐这几部电影"时得靠它还原。

### 时间切分

对每个用户按真实 `timestamp` 排序。只有训练、验证、测试边界满足严格的 `train < validation < test` 时，才把最后两次正交互依次留作 validation/test；边界同秒无法判定真实先后的用户全部留在 train，不能用 `item_idx` 冒充时间。

为什么不能随机切？因为随机切会让模型在训练时看到"将来"。举个具体的：用户 A 在 3 月看了《星球大战》，5 月看了《帝国反击战》。随机切分可能把 5 月那条放进训练集、3 月那条留作测试。模型于是在训练时已经知道"这个用户看过《帝国反击战》"，再去预测他会不会看《星球大战》——而现实中后者发生得更早，模型本不该知道。

问题在于这种泄漏**不会让分数变得离谱**。它往往只是让离线指标"好得有点可疑"，没有报错，没有 NaN，你只会以为模型效果好。

所以这套协议回答的是：**只用过去，能不能预测下一次交互。**

这里有一个常见误读要说清楚：held-out 是**对当前用户而言**的。validation/test 那条交互没有出现在该用户的 train history 里，但对应电影完全可能被其他用户在 train 中看过。所以这不是全局 cold-start 切分，别拿它当"冷启动评测"来解释结果。

交互不足 3 条、或末尾两道时间边界存在并列的用户，全部留在 train，不进入 validation/test。

### 三个容易被混淆的用户数

跑一次数据准备会打印：

```text
users=6,038 items=3,533 train/val/test=569,231/3,025/3,025
```

三个数字都跟用户数有关，含义却不同：

| 数字 | 含义 |
|---|---|
| 6,040 | MovieLens-1M 的原始用户数 |
| 6,038 | 按 `rating >= 4` 筛完正反馈后**进入模型**的用户数（有两个人的评分全部低于 4） |
| 3,025 | 正反馈至少 3 条且两道末尾时间边界严格有序、因此**可以参与评测**的用户数 |

Embedding 表的行数是 **6,038**，不是 6,040；评测分母是 **3,025**，不是 6,038。旧协议报的 6,035 是把同秒边界的用户也算了进去，现在这类用户整个留在 train，不当分母。

## 二、表示：为什么是两座塔

### 两张独立的表

用户和物品是两套互不相干的编号系统。用户 0 和电影 0 之间没有任何关系，只是都从 0 开始编号。

本项目用两张独立的 Embedding 表，各自持有自己的参数。共用一张表并非不可行（有些实现对参数量敏感时会这么省），但那样"用户 5"和"电影 5"会共享同一个向量，两个无关实体的更新搅在一起——没有特别理由，不必引入这种干扰。

至于为什么叫"塔"——实际系统里两侧通常不是裸查表，而是各自接一段网络（MLP、序列模型等）。"塔"指的是各自的编码器，不是表本身。

### 输出维度必须相同，内部结构可以不同

如果最后一步是直接做 dot product：

```text
score(u, i) = e_u · e_i = Σ_{d=1}^{D} e_u[d] · e_i[d]
```

那么两侧**输出**向量的维度必须相同，否则这个式子写不出来。

但这条约束只落在输出上。两侧塔的内部结构完全可以不一样：用户塔三层 MLP、物品塔两层可以；各自的 embedding 宽度和 hidden 宽度也可以不同（128 对 64 都行），只要最后都投影到同一个 `D` 维空间。

本项目的最简版本两侧都是裸查表，所以"输出维度"就等于 embedding 表的宽度，这两件事暂时还没分开。给两侧加上 MLP 之后就会看到它们的区别，那是第 05 篇的事。

### 共享空间是被目标逼出来的

维度相同只是形式前提，真正要做的是让两侧向量**可比**。

这里有个直觉上的坎：用户向量和物品向量各自随机初始化、各自训练，凭什么它们的内积有意义？答案是第 02 篇那个 `B×B` 分类目标——它会把该配对的用户和物品往同一个方向推，把不该配对的推开。空间不是天然共享的，是训练逼出来的。

## 三、L2 normalize：为什么放在塔的出口

### 公式

不做处理时，内积同时受方向和长度影响：

```text
e_u · e_i = ||e_u|| · ||e_i|| · cos(e_u, e_i)
```

一个模长大的向量，哪怕方向完全不相关，内积也可能很大。模型于是可以走捷径：把热门物品的向量学得特别长，就能在排序里占便宜。这不是我们想要的信号。

L2 normalize 把长度除掉：

```text
ê = e / ||e||_2 ,        ||ê||_2 = 1
```

归一化之后内积只剩方向：

```text
ê_u · ê_i = cos(e_u, e_i) ∈ [-1, 1]
```

### 为什么放在"塔的出口"而不是模型出口

因为检索时两侧是**分开使用**的。

Two-Tower 的整个卖点在于 item 向量可以离线预先算好、建成索引，线上只需编码用户再查一次近邻。这要求 `encode_items()` 和 `encode_users()` 的返回值本身就是最终用于比较的向量。

如果把 normalize 放在 `forward` 的最外层，单独调用 `encode_items()` 拿到的就是未归一化的向量，训练和检索两边的相似度定义不一致了。

### 边界：这不是 Two-Tower 的必要条件

L2 normalize 是一个**设计选择**，不是 Two-Tower 的定义。

改用内积或欧氏距离，都能构建合法的双塔。选 cosine 的代价是丢掉模长信息——某些场景下长度本身是有用的（比如把活跃度编码进长度），这时 normalize 反而是损失。这里选它，是为了让训练时打的分和检索时打的分口径一致。

另外注意：`[-1, 1]` 这个范围对 softmax 来说偏窄，所以还需要一个 temperature 来放大。那是第 02 篇的事。

## 四、这一篇的两个坑

1. **随机切分造成的泄漏不会报错**，只会让离线指标虚高。看到分数异常好，第一件事是回去核对切分方式，而不是庆祝。
2. **三个用户数混用**。Embedding 行数是 6,038，评测分母是 3,025。写报告时混了，指标全错。
