# 05｜同一份权重，两个数

第 04 篇留下了 `best_epoch = 30` 的权重。这一篇把它送进评测，然后回答一个前面一直绕着走的问题：**0.095537 和 0.193058 到底能不能放在一张表里。**

结论先给：不能直接比，但有两个可以比的口径。这一篇把两种协议的分工讲清楚，然后给出交付表。

## 一、序列评测和 ID-only 评测不是同一个问题

两类模型看到的"历史"不一样：

| | 历史（模型输入） | 已看过滤集 |
|---|---|---|
| Popularity / MF / Two-Tower | train | train |
| SASRec（标准序列协议） | train + validation | train + validation |
| SASRec（train-only 补充） | train | train |

为什么序列模型可以有那条 validation 历史？因为在定义的时间顺序里，**validation 交互发生在 test 目标之前**。到 test 目标的时刻为止，"用户看过什么"这个集合里确实包含 validation 那一条。这不是特权，是序列模型天然能吃到的信息。

两条必须同时成立的边界：

- **目标物品本身永远不进输入序列。** 这一条和上面那条不矛盾：validation 交互是历史，test 目标是答案。
- **过滤集和输入集一致。** 用 train + validation 当历史，就必须把这两个集合都从候选里剔掉；只用 train 当历史却过滤掉 validation 的交互，等于把用户没看过的物品当成看过的，指标会偏低且没有意义。

那么"ID-only 模型也该把 validation 加进历史"吗？不能。ID-only 模型的输入是 `user_idx` 查表，没有"历史"这个入口——它的用户向量在训练时就固定了，加不加 validation 都一样。所以两边天然不在同一条起跑线上。

## 二、要比较，就得做一次口径对齐

仓库的做法是额外跑一次 train-only 的 SASRec：

| SASRec | 历史 | test Recall@10 | test Recall@20 | test NDCG@10 | test NDCG@20 |
|---|---|---:|---:|---:|---:|
| 标准协议 | train + validation | 0.128264 | 0.193058 | 0.065463 | 0.081787 |
| train-only 补充 | train | 0.101818 | 0.160331 | 0.051757 | 0.066413 |

于是有两种可比的陈述：

- **标准序列评测**：`SASRec = 0.193058`。这是"如果我能用到所有已观测历史"的结果，也是这个权重最自然的成绩，但它不能和 Two-Tower 的 0.095537 相减。
- **历史协议的受控输入对照**：`Two-Tower 0.095537 → SASRec 0.160331`，差约 68%。两者除了历史使用方式，训练目标、采样和训练预算也不同；因此这只是模型配置之间的观察差异，不能把 68% 全部归因于序列建模。

同一份权重在两个协议下差 0.033（0.193058 - 0.160331）。这个差值本身就是"多一条历史值多少"——它比第 03 篇里那几个消融的效应都大。换句话说，**在这份数据上，"能看到什么"比"模型结构怎么调"重要。**

labs 里把同一件事重做了一遍：Lab 5 训一份 30 轮的权重（validation Recall@20 = 0.230000），Lab 6 用它跑两种协议，评测用户是 validation 排序后的前 800 个：

```text
协议              平均历史长度   Recall@10   Recall@20   NDCG@20
train-only          40.0        0.103750    0.170000    0.074801
train+validation    40.4        0.140000    0.208750    0.092204
                                          +0.038750   +0.017403
```

两点值得单独说：

- **平均历史长度几乎没变（40.0 → 40.4），指标却涨了 0.03875。** 多出来的历史只有一件物品，在均值上几乎看不见，但它是"最近发生的那一件"。用平均长度衡量"历史长了多少"在这里会骗人。
- Lab 6 的 `evaluate_locked_test` 在 labs 自己那套评测流程上跑协议 A，得到 `Recall@20 = 0.154050`。这是 labs 的数，和 `src/` v2 的 0.160331 不能直接对——两边的训练预算、评测用户和实现细节都不同。

## 三、评测要检查的三件事

**1. 目标物品不在输入里。** 序列模型的评测输入是从历史构造的，而历史里多一条 validation 就多一次"不小心把目标拼进去"的机会。`labs/lab5` 把这条写成了断言：目标物品既不在输入序列里，也不在 seen 集合里。

**2. 已看物品必须从候选里剔掉。** 不然模型把用户昨天看过的电影排在第一位，指标会虚高。做法是把这些位置的分数压成 `-inf`，再 `topk`。用 `0.0` 代替 `-inf` 不行：分数本来就不保证是负的，`0` 很可能仍然排在前面。

**3. 候选集是怎么定义的。** 本项目的物品表在切分**之前**建立：6 个物品在所有用户的训练集里都没有出现（其中 3 个是 validation 目标、3 个是 test 目标）。它们的 embedding 拿不到任何训练信号，却仍然参与排序。这是冷启动限制，不是泄漏——它们的身份是已知的，只是模型没有机会学会它们。

## 四、指标本身的三个注意点

**Recall 和 HitRate 在这里是同一个数。** 留一法评测里每个用户只有一个相关物品，`Recall@K = 命中数 / 相关数 = 命中数 / 1`，而 `HitRate@K = 命中用户数 / 用户数`。两者恒等，同时列出不是两份独立证据。文档里保留两列只是因为工程的指标模块统一输出，读的时候要知道它们是同一个数。

**NDCG 把名次算进去了。** 命中同一部电影，排第 1 和排第 20 对 Recall 一样、对 NDCG 不同。这也是为什么第 03 篇那个"去掉因果 mask"的消融里，Recall 和 NDCG 都涨——两个指标在同一个方向上。

**候选集是全量还是采样。** 本项目是全量排序（全部 3533 个物品参与）。采样评测（从全量里随机抽一部分候选算指标）会系统性高估模型，而且不同采样规模之间不可比——这一点在 Krichene & Rendle 那篇里有详细讨论，也是这类实验里最常见的"看起来很好"来源之一。

## 五、一个数据层面的限制

MovieLens 的时间戳是秒级的。历史 v1 切分中，**1,903 个评测用户的 validation 和 test 交互落在同一秒**；用 `(timestamp, item_idx)` 排序虽然可复现，却不能证明真实先后。v2 不再用 item ID 假装时间：只有 train < validation < test 严格成立的用户才参与留出评测，边界有同秒并列的用户全部留在 train。

v1 的问题记录在 `artifacts/legacy_protocol_v1/results.json` 的 `evaluation_protocol` 中；v2 的实际规模和指标以 `artifacts/results.json` 为准。v2 测试时只有时间严格早于测试目标的 validation 行为可作为历史，目标本身不会进入输入。

## 六、交付表

配置锁定之后，test 只跑一次。四个模型在同一份切分、同一套指标下的结果：

| Model | Recall@10 | NDCG@10 | Recall@20 | NDCG@20 |
|---|---:|---:|---:|---:|
| Popularity | 0.050248 | 0.024535 | 0.083636 | 0.032910 |
| MF | 0.064463 | 0.031490 | **0.103140** | **0.041186** |
| Two-Tower | 0.055207 | 0.028994 | 0.095537 | 0.039122 |
| SASRec（标准协议） | **0.128264** | **0.065463** | **0.193058** | **0.081787** |
| SASRec（train-only） | 0.101818 | 0.051757 | 0.160331 | 0.066413 |

交付时要说清的几件事：

- 前四行的口径相同，可以直接比；**最后一行是为了对齐口径补的，它和 SASRec 标准协议那一行也不能互相比较**——它们是同一个模型的两个问题。
- validation 上的数通常比 test 高（例如标准协议下 validation Recall@20 = 0.197686 对 test 0.193058）。这是正常的：**validation 上做过模型选择，天然带一点乐观偏差。这个差值不是"过拟合"的证据**，也不该拿它当早停依据。
- Popularity 只有 0.083636，这是"按训练集热度排序"的非个性化下界。Two-Tower 的 0.095537 只比它高 14%，MF 还比它高——**所以这份交付表里，ID-only 三个模型之间的名次不要当结论读**，它们都在热门榜附近。

## 七、该用哪个协议

不是"哪个数字高用哪个"，而是取决于你要回答的问题：

| 想问的问题 | 用哪个协议 |
|---|---|
| 这个模型作为序列模型能做到多好 | 标准序列协议 |
| 序列建模相比静态画像值多少 | 口径对齐（都用 train 历史） |
| 线上会是什么表现 | 都不是——离线留一法本身就和线上有差距 |

最后一行值得强调：这份评测是留一法（每个用户一个目标物品、全量候选、过滤已看）。真实系统里用户下一次交互可能是多个候选、可能落在物品表之外、还可能被位置和曝光影响。**离线指标的作用是在同一套协议下做相对比较**，把它当成线上效果的预测值是另一件事。

## 这一篇的坑

1. **把两个协议的数字并列成"模型对比"**。列在同一张表里必须说明口径，否则 0.193058 会被读成"序列模型比双塔强一倍"。
2. **目标物品混进评测输入**，指标虚高且不报错。
3. **过滤集和输入集不一致**：用 train 当历史却过滤 validation，或反过来。
4. **用 `0.0` 代替 `-inf` 屏蔽已看物品**。
5. **把 Recall 和 HitRate 当成两个指标**。留一法下它们恒等。

## 文献

- **SASRec**：Kang & McAuley, *Self-Attentive Sequential Recommendation*, ICDM 2018（[arXiv](https://arxiv.org/abs/1808.09781)）——4.1 节定义了这套"留一法 + 全量排序"的评测流程，本项目的协议沿用它的设定。
- **Sampled metrics**：Krichene & Rendle, *On Sampled Metrics for Item Recommendation*, KDD 2020（[ACM](https://dl.acm.org/doi/10.1145/3394486.3403226)）——采样候选评测为什么会系统性高估、以及不同采样规模之间为什么不可比；这一篇关于"全量排序"的选择就是冲着这个来的。
- **基准复现**：Dacrema, Cremonesi & Jannach, *Are We Really Making Much Progress? A Worrying Analysis of Recent Neural Recommendation Approaches*, RecSys 2019（[arXiv](https://arxiv.org/abs/1907.06902)）——对神经网络推荐论文的可复现性和基线选择做的系统检查，可以直接用来对照"为什么必须先跑 Popularity 基线"这件事。
