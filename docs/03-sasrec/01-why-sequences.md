# 01｜用户向量装不下的东西

前五篇里，用户被压成一个 128 维向量。这个向量在训练中被反复调整，试图同时装下他所有的兴趣。问题出在"同时"两个字上。

这一篇说的不是"序列模型更强"，而是一件更基础的事：**同一个用户的第 1 次行为和第 50 次行为，在静态画像里没有任何区别；在序列模型里是两条独立的训练信号。** 差别有多大，以及为什么不能拿两边的指标直接比，是这一篇要交代的。

## 一、静态画像的天花板在哪

Two-Tower 的用户表示只有一个来源：查表。

```text
e_u = user_embedding[u]          # [D]
score(u, i) = e_u · item_embedding[i]
```

无论这个用户有 5 条历史还是 1433 条历史，无论他昨天刚看了什么，`e_u` 都是同一行参数。训练时它被所有历史交互往同一个方向拉，最终收敛到一个"平均兴趣"的位置。

在 MovieLens 的历史协议上这会丢掉什么？下面是当时的实测分布；原始探针产物未随仓库保存，不能作为新协议统计使用：

```text
训练集里有历史的用户: 6,038
序列长度 中位数 / 均值 / 最长: 56 / 93.3 / 1433
序列长度超过 50 的用户: 5,447  （90.2%）
```

也就是说九成用户的兴趣演化被压成了一行 128 维参数。一个用户在 2000 年给儿童片打了高分、2010 年开始看黑色电影，模型对他的刻画是两者的折中——而那 1433 次行为里的时间顺序，在查表这个动作里完全没有入口。

## 二、换成"每个位置各预测下一个"

SASRec 把输入改成最近 50 个物品的序列：

```text
input:  [i_1, i_2, ..., i_50]
```

对长度为 6 的序列 `[a, b, c, d, e, f]`，切法是整体错开一格：

```text
输入   a  b  c  d  e
目标   b  c  d  e  f
```

一次 forward 同时产出 5 个位置的隐状态，每个位置各自预测它的下一个物品。两个后果：

- **监督信号的数量级变了。** Two-Tower 一个 batch（`B=256`）产生 256 条配对监督；SASRec 一个 `[256, 50]` 的 batch 最多产生 12800 条逐位置监督（实际有效位置略少，末尾有补齐位）。
- **用户表示变成动态的。** 序列末位的隐状态是通过注意力汇总它左边所有位置得到的，看什么历史就有什么表示。"最近看了什么"第一次有了入口。

代价是用户不再是一个稳定的实体。Two-Tower 可以把全部用户的向量离线算好存起来；SASRec 的表示随序列走，而序列每次交互都会变。这个代价在召回侧是真实的，第 05 篇会回到它。

## 三、0.096 和 0.193 不能直接相减

到这里很容易顺手写一句"序列模型把 Recall@20 从 0.096 提到 0.193，翻了一倍"。**这两数不属于同一个评测协议，不能这么减。**

差值来自历史长度和过滤集：

| | 历史（模型输入） | 已看过滤集 | test Recall@20 |
|---|---|---|---|
| Two-Tower / MF / Popularity | train | train | 0.095537 |
| SASRec（标准协议） | train + validation | train + validation | 0.193058 |
| SASRec（train-only 补充） | train | train | 0.160331 |

读法：

- 标准序列评测里，test 目标发生的时刻**验证集交互早已被观测到**，所以模型允许把 validation 那条也放进输入序列。这不是泄漏——validation 在定义的时间顺序里排在 test 目标之前，目标本身从不进入输入。
- ID-only 的三个基线没有这种"多一条历史"的机会。为了口径公平，仓库额外跑了一次 train-only 的 SASRec：**0.160331**。
- 于是正确的说法是：**在完全对齐的历史和过滤集下，0.095537 → 0.160331**；标准协议下的 0.193058 是同一份权重换更长的历史得到的，属于另一个问题。

这两个数之间约 +68% 的差异里，还混着目标函数、负采样和训练预算的不同，不能单独归因于静态画像与序列表示；把 0.193 说成"Static 的两倍"同样混入了不同测试历史。第 05 篇会说明协议差异。

## 四、序列模型不是"更大的 Two-Tower"

有两处容易想混，先划清边界。

**它不是把用户历史求和喂进 MLP。** 把 50 个物品向量取平均、或者按时间衰减加权求和，也能得到一个"看过什么"的表示，那是另一条路线（通常叫 pooling）。区别在于：pooling 对所有位置一视同仁（或只按时序衰减），而注意力可以按内容决定看谁——喜欢黑色电影的用户在预测下一部时，2003 年那部同类片应该比 2010 年那部喜剧更相关，这个权重是学出来的，不是按时序给的。

**它也不是 Two-Tower 的替代。** 工业系统里两者通常并存：序列模型算得贵，只能对活跃用户、在精排或近线召回里用；海量冷用户的召回还是靠双塔甚至热门。这个仓库把它们摆在一起对照，是因为它们回答的是同一个问题（下一步推什么）的两条路线，而不是新旧版本。

## 这一篇的坑

1. **拿 0.193 和 0.096 直接比。** 两个协议的历史和过滤集都不同；要对齐口径就看 0.160331。
2. **把"多一条 validation 历史"当成泄漏。** 关键是目标物品本身不能进输入，而且 validation 在时间顺序上确实早于 test 目标。这两条都要成立才算合法，缺一条就是泄漏。
3. **以为序列越长越好。** 这份数据里用户序列长度中位数 56，`L` 加到 200 时一半以上的位置是补齐位——白算，还要付 `O(L²)` 的注意力开销。

## 文献

- **SASRec**：Kang & McAuley, *Self-Attentive Sequential Recommendation*, ICDM 2018（[arXiv](https://arxiv.org/abs/1808.09781)）——把因果自注意力用于下一物品预测的代表作，本项目实现的直接来源；论文里对"序列模型 vs 静态 MF"的对照实验是这一篇的历史依据。
- **BERT4Rec**：Sun et al., *BERT4Rec: Sequential Recommendation with Bidirectional Encoder Representations from Transformer*, CIKM 2019（[arXiv](https://arxiv.org/abs/1904.06690)）——把单向换成双向掩码预测的后续工作，可以用来说明因果约束是一个可权衡的设计选择，而不是唯一的做法。
- **FPMC / GRU4Rec**：Rendle et al., *Factorizing Personalized Markov Chains for Next-Basket Recommendation*, WWW 2010（[ACM](https://dl.acm.org/doi/10.1145/1772690.1772773)）；Hidasi et al., *Session-based Recommendations with Recurrent Neural Networks*, ICLR 2016（[arXiv](https://arxiv.org/abs/1511.06939)）——序列推荐在注意力之前的两条路线：马尔可夫链和 RNN。对照着看能明白"用序列"这件事本身不等于"用注意力"。
