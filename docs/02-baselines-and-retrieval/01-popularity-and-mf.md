# 01｜先跑一个热门基线

前两个系列里，模型越来越复杂：查表 → 两层塔 → 因果注意力。这一篇往回退一步，写两个更简单的模型，因为它们回答一个前面的文章一直回避的问题：**0.095537 到底是好是坏？**

没有参照物的时候，"Recall@20 = 0.11" 看不出任何东西。它可能意味着模型学到了个性化，也可能意味着"在这个数据集上，随便推热门就有 0.11"。

## 一、Popularity：一个没有参数的模型

```text
1. 数一遍训练集里每个物品被交互了多少次
2. 按次数降序排好，得到一张全局榜单
3. 对每个用户：从上往下扫，跳过他已经看过的，取前 K 个
```

它没有任何可训练的参数，也没有"用户"这个概念。它回答的问题是：**如果我对这个用户一无所知，只知道全站什么最火，能有多准？**

实测（`labs/lab7` 的 `✅ 跑一下`）：

```text
Popularity   val Recall@20 0.079205   val NDCG@20 0.030081
```

早先那份完整流程跑出来的是 **0.0792046**——当时两个实现（labs 手写 vs `src/recsys/models/popularity.py`）几乎逐位相同。v2 换了切分和过滤口径，这个数不能当当前的对照。

三个实现细节会直接影响这个数：

**每个用户的候选要现过滤。** 全局榜单是所有人的，但"这个用户没看过"是每个人的。推荐全局 Top-K 而不过滤，会给每个用户推同一批他已经看过的电影——指标会低得莫名其妙，而且你会以为是模型问题。

**次数相同时排序必须确定。** `sorted` 是稳定的，但那只保证"输入顺序相同则输出相同"。用 `(-count, item_idx)` 当键，才让结果不依赖输入的排列方式。评测里"同样的代码跑出不同的数"是最难查的一类问题。

**榜单是训练集的，不是全量的。** 用测试集的正反馈去数次数，等于把答案混进了模型——这类泄漏在非参数模型里更容易被忽略，因为它"没有训练过程"。

## 二、Popularity 的两种正确用法

它的第一重身份是**下界**。所有报告出来的数都应该离它足够远：

| Model | test Recall@10 | test Recall@20 | test NDCG@20 |
|---|---:|---:|---:|
| Popularity | 0.050248 | 0.083636 | 0.032910 |
| MF | 0.064463 | **0.103140** | 0.041186 |
| Two-Tower | 0.055207 | 0.095537 | 0.039122 |
| SASRec（标准序列协议） | **0.128264** | **0.193058** | **0.081787** |

Two-Tower 的 0.095537 相比 Popularity 的 0.083636 只高 14%——而且 MF 的 0.103140 还比它高。早先的宽松协议下这个差距是 65%，换成严格时间切分之后缩到了四分之一左右。

**所以在 v2 上，"个性化比热门榜强多少"的答案比之前保守得多。** 如果你只是想确认管道没写错，14% 够用；但如果要拿它当"模型确实学到了东西"的强证据，现在不够。

第二重身份是**失败诊断**。模型指标低于 Popularity 时，几乎不可能是"模型容量不够"，而是：

- 切分错了（训练时看到了未来）；
- 评测时的已看过滤漏了；
- loss 的掩码或对齐写错了，模型在优化一个错的目标；
- 数据编码错位（比如 `+1` 加了两遍）。

这四种都不报错，只让指标偏低。所以**先跑 Popularity，再跑任何复杂模型**——它是唯一一个"如果它也算不对，就说明评测本身有问题"的模型。

## 三、MF：和 Two-Tower 只差一个目标

MF 的结构是 Two-Tower 的最简版本（或者说 Two-Tower 是 MF 加了一个 batch 内目标）：

```text
MF         : logits = user_emb[u] · item_emb[i]        # 一对一打分
Two-Tower  : logits = batch 内每个用户 × 每个物品       # [B, B]
```

参数形状几乎一样，差别全在"一次更新能看到多少个候选"：

| | MF | Two-Tower（in-batch） | SASRec |
|---|---|---|---|
| 每个正样本配几个负样本 | 1 个（随机采） | 最多 B-1 个（单向 in-batch；mask 后更少） | 1 个（逐位置） |
| 一个 batch 的候选位置数 | B | B² | B×L（扣补齐） |
| 负样本可能撞上别的用户的正样本 | 不会 | 会（21.1%） | 不会 |

`docs/01-two-tower/04` 量过那个 21.1%，是 in-batch 目标的固有代价。

### in-batch 目标缺了 temperature 会退化

`labs/lab7` 做了一组对照：同一个 MF、同一批数据、同样的 epoch 数，只换负采样方式。结果和"负样本越多越好"的直觉不一样：

```text
配置                    最后一轮 loss   |user|   |item|   val Recall@20
MF random                0.5092       4.636    5.104    0.110522
MF in_batch（无 T）       5.8517       4.135    3.862    0.061475
MF in_batch（T=0.1）      6.4083       1.477    1.209    0.044242
Two-Tower（mask, T=0.1）  3.7380      11.169   10.911    0.110688
```

先看 `|user|` / `|item|` 这两列——它们才是这个实验的重点。

in-batch 的交叉熵只关心正样本的分数大不大，而分数是 `e_u · e_i`。**把所有向量一起缩小，正样本分数靠近 0，交叉熵就能降下来**，完全不需要学任何区分性信息。这就是退化解：loss 看着在降，两张表在往零收缩，所有物品的分数挤在一起，排序能力被压平。

temperature 是钉住这个尺度的旋钮（`logits = scores / T`，再算交叉熵）。`T` 越小，同样的向量长度对应越尖的 softmax，模型就必须靠"方向对不对"而不是"长度小不小"来降 loss。

**但这里还有第二层：** 加了 temperature 的 in-batch 反而更差（0.0442）。说明"钉住尺度"并没有让它赢过最简单的随机负采样。两个目标在优化不同的东西：

| | 每个正样本的对手 | 在优化什么 |
|---|---|---|
| `random` + BCE | 1 个确定的负样本 | "这个物品比那个好" |
| `in_batch` + CE | 200~300 个候选 | "这个物品在一堆里排第一" |

后者的候选集是**这批数据里恰好出现的物品**，由采样顺序决定、每轮都不一样。候选更多、但判据更难稳定。

### 两个模型打平了

```text
MF random               0.110522
Two-Tower（mask, T=0.1） 0.110688     （差 0.0002）
```

这不是巧合：embedding-only + in-batch + `T=0.1` 的 Two-Tower 就是 MF 加一个 batch 内目标。加上 temperature 之后它不再退化，于是两组学到同一量级的东西。

**所以这一组的结论不是"Two-Tower 比 MF 强"**，而是：在这份数据、这个预算下，最简单的"一个正样本配一个随机负样本"就是最强的方案；换成 in-batch 要额外把 temperature 调对，调对之后也只是打平。**复杂度要换来东西才值得，这一组没换到。**

`results.json` 里 MF 的 0.103140 反而高于 Two-Tower 的 0.095537。两者都是两张 embedding 表加内积，差别在训练目标和训练预算；这个方向翻转说明那点差距在噪声量级，不足以支撑结构优劣的判断——和上面 labs 那组"打平"是同一个结论。

### 多种子确认

单次运行的 0.05 差距，按 `docs/03-sasrec/03` 的教训还要看种子抖动。三种子复跑（训练 1200 个用户 + 同规模评测）：

| 配置 | Recall@20 均值 | 极差 |
|---|---:|---|
| MF random | 0.112222 | [0.1075, 0.1175] |
| MF in_batch（无 T） | 0.058611 | [0.0542, 0.0633] |
| MF in_batch（T=0.1） | 0.040000 | [0.0358, 0.0450] |

领先幅度 0.0536 远大于种子极差 0.0100，所以"随机负采样更强"这个结论站得住。**但注意三组都用了同一个训练子集和同一批评测用户**——如果只训一部分用户、却在全部用户上评测，没训过的那些用户 embedding 还是随机值，三组会一起塌下去，差值被淹没。

## 四、这一篇的坑

1. **推荐全局 Top-K 不过滤已看物品。**
2. **排序键只按次数**，相同次数时结果随输入排列变化。
3. **用测试集数热门次数**，非参数模型也会泄漏。
4. **横向比较不同负采样目标的 loss。** `random` 是 `2 ln 2` 量级，`in_batch` 是 `ln(U×I)` 量级，结构决定的差距不是效果。
5. **in-batch 目标忘了 temperature**，向量往零缩、指标塌一半，而 loss 曲线看着正常。
6. **单次运行就下结论**，差值可能小于种子极差。
7. **只训一部分用户却在全部用户上评测**，三组一起变差，误读成"数据少所以正常"。

## 文献

- **BPR**：Rendle et al., *BPR: Bayesian Personalized Ranking from Implicit Feedback*, UAI 2009（[arXiv](https://arxiv.org/abs/1205.2618)）——"每个正样本配一个负样本"这条路线最出名的形式，pairwise 排序损失；本项目的 `random` 分支用的是它的 pointwise BCE 版本。
- **NCF**：He et al., *Neural Collaborative Filtering*, WWW 2017（[arXiv](https://arxiv.org/abs/1708.05031)）——把 MF 的点积换成 MLP 的系统对照；论文附录讨论了"每个正样本采几个负样本"的影响，也是"MF 和神经网络模型差别到底在哪"的早期讨论之一。
- **Sampled metrics**：Krichene & Rendle, *On Sampled Metrics for Item Recommendation*, KDD 2020（[ACM](https://dl.acm.org/doi/10.1145/3394486.3403226)）——负样本数量不只改变训练信号强度，还改变指标的读法；本项目坚持全量排序评测就是冲着这一点。
